- 2026-11-11: Added a sensitivity analysis to Section 5, fixed on MMPD-A (development data). On MMPD-B, recordings whose background shows a periodic peak near 2.0 Hz or 3.0 Hz are excluded, and C1–C4 are repeated. The background signal is the mean of the R, G and B values over the pixels outside the face box in each frame. The face box is the one used for the PhysNet input view: a fixed OpenCV detection on the first frame, enlarged as for that view and clipped to the frame. The spectrum is a Welch estimate on the 512-point HR grid at 30 fps: linear detrend of the whole signal, Hann window, 300-sample segments with 150-sample overlap, segment means removed. A recording is flagged when this spectrum has, in bins 33–35 (116.02–123.05 bpm) or 50–52 (175.78–182.81 bpm), a bin that is larger than both neighbours and at least twice the median of the six surrounding bins, three on each side. Recordings without background pixels are left out of this analysis. The implementation is src/stage5/mmpd_background_flags.py.
- 2026-11-13: Inference batching, random numbers and two sensitivity analyses. The evaluation of Sections 3 and 4 is not changed.
  1. Batching. In the inference code used for all arms, FactorizePhys outputs are standardized with the mean and standard deviation of the whole inference batch, as in the rPPG-Toolbox FactorizePhys test code (commit b7500b8). With FSAM enabled, its BVP head also uses the batch-wide minimum. FactorizePhys outputs therefore depend slightly on which chunks share a batch: in a development check on 30 MMPD-A windows, changing the batching changed the standardized waveform by up to 0.40 and the narrow-band HR readout of one window. PhysNet and RhythmFormer waveforms changed by at most 0.044, with no change in HR. The batching is fixed for all backbones and arms. MMPD-B: the chunks of the October input plan in its full order, four chunks per batch; batches may cross recording boundaries, and the last batch holds the remaining chunks. This is the batching used for MMPD-A, and the comparison of the re-inferred original-arm predictions with the stored October predictions (Section 3, Run) also verifies it. MCD-rPPG test half: per recording, chunks in temporal order, four chunks per batch; the last batch of a recording holds the remaining chunks. This is the batching used for the development half.
  2. Random numbers. The per-recording reset of the random-number state stays in place. In this code revision inference uses no random numbers: the FSAM basis is initialized with ones and dropout is inactive at evaluation. The reset therefore has no effect.
  3. FSAM. For FactorizePhys, the confirmatory contrasts are also reported with FSAM disabled at inference, as a sensitivity analysis.
  4. Line-removal input. No line-removal input procedure is fixed, so this sensitivity analysis of Section 5 is omitted. On the development half, RhythmFormer was re-inferred after removing, at each pixel, the mean deviation of each of the 12 frame phases of the key-frame interval from that pixel's overall mean. The key-frame-line fraction of high-HR windows fell by 0.012 to 0.071 across arms, and the contrasts changed by at most 0.53 bpm in high-HR MAE and by at most 1.12 bpm in low-HR MAE. This is reported as an exploratory result.

  4. Test-run protocol. The test run uses the evaluation script at commit 19ecf5d, which reproduced the development results before this entry, gave identical prediction files when run twice on the same development inputs under the guard below, and gave the same confirmatory results when the predictions of one exploratory checkpoint were left out. The code is published at commit 19ecf5d; in the files listed in docs/A4_REDACTIONS.csv, values that are machine-specific paths are replaced by placeholders. docs/A4_CODE_SHA256.txt gives the SHA-256 of every code file as run, and docs/A4_CODE_SHA256_THIRD_PARTY.txt that of the third-party rPPG-Toolbox files; before each stage the files to be run are checked against these lists. The test run has three stages. Each stage is started by the command recorded in eval5/drive/step.sh at commit 19ecf5d, which takes no arguments other than those fixed there (expected recording count of MMPD-B: 435, from 22 subjects, as in the October code); stage (b) is started only through run_test_b_locks.sh at the same commit, which holds the locks of both GPUs until the stage has ended. Stage (b) runs on GPUs that no other job uses until stage (b) has ended, with the GPU model and software environment of the rehearsal. The allocator's out-of-memory count is recorded for every checkpoint, and stage (b) stops and is repeated from its start if an out-of-memory event is reported, because the convolution library then silently changes its computation plan and with it the outputs. Face detection runs in every stage on a single CPU thread, with OpenCL disabled in OpenCV and the GPU hidden from the detection processes, so that neither the order of two equally large detections nor the device on which the detector runs can change between runs; the number of test recordings whose first frame has two or more equally large detections is reported. The SHA-256 hashes of the outputs of each stage are committed, and an OpenTimestamps proof of the hash file is created, before the next stage starts. The proof is upgraded to a Bitcoin attestation when it becomes available, and the hash file and the proof files are kept in the repository. The commits are pushed to the remote repository before the next stage starts; stage (a) does not start until a push of this entry has succeeded.
     (a) the window lists, reference HRs, high-HR flags, background flags (2026-11-11 entry) and bootstrap index sets of MMPD-B and of the MCD-rPPG test half, generated from the raw data by the October code (for MMPD-B, the October modules st11x.future.mmpd_b_references and pathways.mmpd_b_membership, with src/st3/c4.py, as of commit dbb4535, with only file paths changed and the expected recording count made a parameter; for the MCD-rPPG test half, the code used for the development half, including the recording selection of Section 3), and the frame rate and key-frame interval of each MCD-rPPG test recording, read from the bitstream headers without decoding pixels. Stage (a) also records the SHA-256 of the MMPD-B inference input plan and of the stored October predictions of the original arms on both test sets, which are taken unchanged from the October evaluation; these predictions are read only for the comparison between stages (b) and (c). The MMPD-B window list and reference HRs are compared with the sets of the October evaluation; if they are equal, this is stated with the hash of the October files. If they differ, the cause is established and reported before stage (b): an error of the regeneration is corrected, stage (a) is repeated and both sets of hashes are reported; otherwise the regenerated sets are used, and the confirmatory contrasts are also given on the October sets.
     (b) the saved predictions of every checkpoint in the manifests, confirmatory checkpoints first, including the FactorizePhys predictions with FSAM disabled and with one chunk per batch, written by a process without access to the reference signals;
     (c) the join of predictions and references and all analyses, run once. After the run, every output table is checked against the manifests for missing backbone, arm, contrast or test-set rows. If rows are missing because of an execution error, the error is corrected without changing any analysis and stage (c) is repeated from its start; the repetition must reproduce every row of the first run byte for byte, and any difference is reported.
     Between stages (b) and (c) the predictions are used only for hashing, for the validity checks (defective checkpoints, item 2; window support, below) and for the comparison with the stored October predictions on MMPD-B (Section 3, Run) and, as a descriptive check, on the MCD-rPPG test half. If the comparison on MMPD-B gives a different HR readout for any window, the guarded inference of the affected recordings is repeated before stage (c). If the repetition does not reproduce the stage (b) predictions byte for byte, the inference set-up is corrected, stage (b) is repeated and both sets of hashes are reported. If it does, the difference is attributed to the October run, stage (c) uses the new predictions, and the number of windows with a different readout and the largest difference are reported. If, on either test set, more than 1% of the windows of any checkpoint have a different readout, stage (c) does not start until the cause has been established and reported.
     Window support. This fixes which checkpoints define the common support and does not change the window construction of Section 3. It follows the common-prediction-support rule of the original manuscript, which was defined over the models evaluated then. The confirmatory analyses use the windows with a valid prediction (a finite waveform that covers the whole window) from every confirmatory checkpoint; the number removed is reported. An exploratory contrast uses those of these windows that also have valid predictions from its own checkpoints, and a sensitivity analysis those that also have valid predictions in its own prediction set. A failed exploratory checkpoint therefore does not change a confirmatory result.
     Reruns. A rerun after a technical failure (a crash, an unreadable file or an out-of-memory error) repeats the failed stage from its committed inputs, must reproduce the hashes already committed for that stage, and is reported. An implementation error found in stage (c) after results have been seen is corrected in a new commit without changing a definition of Sections 3–5 or of the entries, and the results before and after the correction are both reported. Rows that the correction does not concern must be reproduced byte for byte.
     The person who runs stage (c), its start time and its log are recorded. No checkpoint, window, rule or metric is changed afterwards.

- 2026-11-20: Post hoc experiments after the test run. This entry is written after the test run of 2026-11-15 and 2026-11-16 and before any run it describes is started.   1. Label representation. PhysNet arms (0), (i), (i-pc) and (i-simple) are trained with standardized labels, made as for rule 5 of docs/STAGE5_DEV_DIAGNOSTICS.md, with three seeds each (12 runs). Items, seeds, initial weights, steps, batch structure, presentation order and loss are those of the confirmatory PhysNet arms; only the labels differ. With the nine runs of rule 5 ((ii), (ii-lag) and (ii-pc)), these arms form the setting PhysNet-Std.

  2. Shift-tolerant loss. Arms (0), (i), (i-pc), (i-simple), (ii), (ii-lag) and (ii-pc) are trained with the maximum cross-correlation (MCC) loss of Gideon and Stent (ICCV 2021) in place of the negative Pearson loss, with three seeds each and everything else unchanged, in three settings: PhysNet with its differenced labels (PhysNet-MCC), PhysNet with standardized labels (PhysNet-Std-MCC) and FactorizePhys (FactorizePhys-MCC); 63 runs. The loss is the authors' published implementation (RemotePPG, MIT licence), including its division by the in-band share of the cross-power spectrum, with two changes: the pass band is 0.6–3.3 Hz (the band of our HR readout) instead of 40–250 bpm, and a batch in which every clip is constant returns a zero that keeps the computation graph. Both signals are mean-removed and zero-padded, their cross-power spectrum is set to zero outside the band, and the maximum over lags of its inverse transform, normalized by the standard deviations of the two signals, is maximized. Unit tests run before this entry showed that the implementation agrees with a direct computation in the time domain and with the authors' code, and that its gradient is finite. On the contact PPG of the training recordings, the median MCC of a prediction shifted by 6, 15 and 30 frames was 0.97–0.98, 0.91–0.93 and 0.88–0.91, and that of an inverted prediction 0.48–0.64; the lag of the maximum recovered a shift only up to whole beat periods, because a lag shorter by one period overlaps the label over more frames. The implementation and these tests are published with the code.

  3. Seeds and pool. For each of the three backbones, arms (0), (i), (i-pc), (i-simple), (ii) and (ii-pc) are trained under the confirmatory settings with three new seeds, 20261148, 20261149 and 20261150, which appear in no code or record of our earlier runs (54 runs). - 2026-11-23: Registered evaluation on VIPL-HR. This entry is written before any video of VIPL-HR is decoded and before any value of its reference signals is read for this study. It adds an external evaluation set; it changes nothing in the earlier entries, and the test run of 2026-11-15 and 2026-11-16 and its results stand as they are. Earlier uses by our group, as stated in item 11 of the entry of 2026-11-20: in October 2026 its reference signals and frame times were read, without decoding its videos or running any model, to plan the test of another study; in August 2026 an earlier study evaluated its own EfficientPhys, PhysNet and FactorizePhys models, trained on PURE or UBFC-rPPG, on it. No arm, setting or analysis of this study was chosen with VIPL-HR. Before this entry, the following were read for this study, and nothing else: the documentation and list files of the dataset; the zip directories, the SHA-256 of the zip files and their CRC tests, which decompress the members without decoding or showing them; the checksums of a copy unpacked by the earlier study, since deleted; the video headers; the frame-time files; and the header lines and line counts of the reference files. No video was decoded and no reference value was read.

  1. Data. VIPL-HR, first release (Niu et al., ACCV 2018; IEEE TIP 2020), read from its 14 original zip files (SHA-256 in docs/A7_VIPL_ZIPS_SHA256.txt): 107 subjects, nine scenes (v1 stable, v2 large head movement, v3 talking, v4 dark, v5 bright, v6 long distance, v7 seated after two minutes of rope skipping, v8 and v9 phone held still and moving) and the additional recordings listed in Additional_data.txt. Only the visible-light videos are used: source1 (Logitech C310), source2 (HUAWEI P9 front camera) and source3 (RealSense F200 colour). The near-infrared videos (source4) are not used. The videos are cropped to the face by the dataset and compressed as MJPG. Nothing is unpacked to disk: each video is passed to the decoder used for the test sets through a file in memory, which is removed after decoding.

  2. Sets. Primary set: every recording of source1 and source3, whose frame times are given in time.txt. Secondary set: every recording of source2, which has no frame times. No scene, subject or recording is selected, except by the exclusions of item 4.

  3. Preprocessing and time axis. The preprocessing of the test run for MCD-rPPG is used: a face box found once in the first frame and enlarged 1.5 times, every original frame cropped to it and resized (72 × 72 for PhysNet and FactorizePhys, 128 × 128 for RhythmFormer), then linear interpolation in time onto a 30-Hz grid from the frame times, without extrapolation, then the normalization and chunks of each backbone. If no face is found in the first frame, the box is the whole frame, which the cropping of the dataset makes appropriate. The frame times are those of time.txt for source1 and source3, and evenly spaced at 30 frames per second for source2, as its documentation states. The BVP record (wave.csv) is placed on the same time axis, starting at the first frame, at the sampling rate fixed by item 6.

  4. Windows and exclusions. Each recording contributes its first five non-overlapping 10-s windows (300 samples at 30 Hz) that lie within both the video and the BVP record. A recording is excluded if its video cannot be decoded, if its time.txt does not have one line per decoded frame, or if it has no complete window; in stage (a) each video is decoded once only to count its frames, and no pixel statistic is computed; a source2 recording is also excluded if its duration at 30 frames per second and that of its BVP record differ by more than 2 s. In the primary analysis, a window that contains an interval of more than 200 ms between consecutive original frames is excluded; a sensitivity analysis keeps these windows. All exclusions are counted and reported.

  5. Reference. The reference HR of a window is read from the BVP by the readout used for the test sets, and a window is verified as for MMPD: no signal defect, and the three model-independent estimates agree (autocorrelation within one bin and median inter-beat interval within two bins of the spectral peak). High-HR windows are verified windows with a reference of at least 100 bpm; low-HR windows are verified windows below 100 bpm. In a sensitivity analysis, the mean of gt_HR over the window replaces the BVP reference; gt_HR is placed at one row per second from the first frame, so that window j takes rows 10j to 10j + 9.

  6. BVP sampling rate. The documentation gives none, and the line counts give 57.1–57.2 BVP samples per row of gt_HR (median by device; gt_HR is recorded once per second). In stage (a), before any prediction exists, the BVP reference of every verified window of both sets is computed at 60 Hz and compared with the mean of gt_HR over the same window. If the median ratio of the two lies within 0.98–1.02, 60 Hz is used. Otherwise the rate of each record is taken as its number of samples divided by its number of gt_HR rows, and the comparison is repeated. If neither rate gives a median ratio within 0.98–1.02, the mean of gt_HR becomes the reference and the BVP, at the rate of each record, is used only to verify windows and to decide whether they lie within the record. The rate used and both comparisons are committed with the outputs of stage (a).

  7. Inference. The readout, verification, inference server, model construction, guards and per-recording inference path of the evaluation code at commit 19ecf5d are used unchanged; FactorizePhys keeps FSAM and is batched per recording, as for MCD-rPPG. Code is added to read VIPL-HR, to build its windows and references and to compute the within-subject change; its SHA-256 is fixed before stage (a).

  8. Checkpoints. Primary: the 45 confirmatory checkpoints of the three backbones, arms (0), (i), (i-pc), (ii) and (ii-pc) with seeds 20261131–20261133, as listed in the stage-5 manifest and its amendment of 2026-11-11. Secondary: the checkpoints of the entries of 2026-11-15 and 2026-11-20, including the nine of rule 5, that exist when this entry is committed; their SHA-256 are listed with it. The retrained checkpoints of item 4 of the entry of 2026-11-20 are not evaluated, because their tensors equal those of the confirmatory checkpoints.

  9. Measures. As for the test sets: high-HR MAE (primary), low-HR and all-window MAE, mean signed error, hit rate and half-HR rate, and the MAE at or above 120 bpm. On the primary set, the within-subject change from rest (v1) to after exercise (v7) is computed for each subject and device with both recordings, from the windows used in the primary analysis and without the additional recordings (MAE, slope and concordance correlation of the change in mean HR), with the crossed bootstrap over subjects and seeds used for the change on MCD-test. The contrasts C1–C4 of these change measures, with seeds paired, are reported with intervals and without tiers.

  10. Statistics, tiers and statements. Intervals use the crossed bootstrap over subjects and seeds of the test run (B = 10,000, seed 20261110).
