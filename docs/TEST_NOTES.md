## Correction to the note on stage (a), 2026-11-16

- The key-frame interval and the container frame rate were read from the bitstream without decoding pixels. The key-frame interval is 12 in all 385 recordings, which contain I and P frames only. The frame rate used for the key-frame frequency is the number of video frames minus one, divided by the time span of the meta timestamp file, as on the development half. It is not the container frame rate, which is 24.0 fps for 127 recordings whose timestamps show 29.90-29.99 fps. On this basis one recording (8772_before, 92.01 bpm) lies outside 147.66-154.69 bpm; on the container frame rate, 127 would. Neither number enters an analysis.

## Stage (b), 2026-11-16

- Stage (b) ran from 12:14:24 to 17:11:43 KST on the two GPUs held by run_test_b_locks.sh. No compute process was on either GPU at the start; GPU use was not sampled during the run. All 261 checkpoints were used, none was defective, and none had an out-of-memory event. docs/TEST_STAGE_B_OUTPUTS_SHA256.txt (commit 094ef73) gives the SHA-256 of the outputs.
- Comparison with the stored October predictions. MMPD-B: no readout of the 27 original-arm checkpoints differs. MCD-rPPG test half: no readout of PhysNet or RhythmFormer differs. Each of the nine FactorizePhys checkpoints differs in 20-33 of its 3,222 readouts (1,611 windows, two layers; 0.62-1.02%), 234 in all, with finite values on both sides and a largest difference of 94.9 bpm. One checkpoint (arm (ii), seed 20261131) exceeded 1%, which stopped the run before stage (c).
- Cause. The October FactorizePhys predictions on MCD-rPPG come from a separate October evaluation, which batched the chunks of all recordings in one order, sorted by file name as text, with batches crossing recordings. The batching of the test half is per recording in temporal order (2026-11-13 entry, item 1), and FactorizePhys outputs depend on which chunks share a batch (same entry). All 234 differing readouts lie in the 1,448 windows per checkpoint whose batch members differ between the two runs; none lies in the 163 windows whose batch members are the same.
- Re-run. step.sh starts the re-run of the recordings with differing readouts after the check. It started it with the main Python environment, in which the checkpoints did not load, so no prediction was made. The re-run was repeated once with unchanged code and arguments under the Python environment of stage (b), on GPU 0 with both GPUs held, and reproduced the stage-(b) predictions of all 54 checkpoints on the 74 recordings byte for byte. The failed attempt is listed in docs/TEST_STAGE_B_OUTPUTS_SHA256.txt; the hashes of the re-run outputs were committed before stage (c).
- The stop was released before stage (c) with this cause, recorded in docs/TEST_STAGE_B_STOP_RELEASE.txt. Stage (c) uses the stage-(b) predictions.
